# Research & Design Decisions: optimized-interpreter

---
**Purpose**: 最適化インタプリタの設計に至る調査・判断・トレードオフの記録。`design.md` は自己完結しており、本書は背景の補足である。
---

## Summary
- **Feature**: `optimized-interpreter`
- **Discovery Scope**: Extension(既存 workspace に `brainfuck-core` を入力とする新 crate を追加する。core は変更しない)。ただし「意味保存」の設計判断が重いため、軽量発見に加えて意味論の個別検証を行った
- **Key Findings**:
  - 最適化の成否は「速さ」ではなく「エラー位置・ステップ制限の境界を含む観測的一致」で決まる。融合/ループ最適化は、途中で範囲外・ステップ上限に当たりうる場合の状態再現が最大の設計課題
  - 素朴実装換算の実行数は、融合操作・最適化ループのいずれでも**事前に閉形式で厳密に計算可能**(下記「実行数の閉形式」)。したがって上限判定は「操作を実行する前に残り予算と比較する」だけで素朴実装と同じ境界を再現できる
  - 一括適用が意味を保てない稀なケース(範囲外・予算不足)は、**その操作の先頭から素朴意味論でそのまま再生する縮退経路**に切り替えれば、エラー時の状態・`pc` が素朴実装と構造的に一致する。縮退経路が走るのは必ずエラー(または予算切れ)の直前であり、性能には影響しない
  - core の `MachineSnapshot` は `#[non_exhaustive]` のため core 外から構築できない。最適化側は独自のスナップショット型を持つ
  - core の `RuntimeError` / `StopReason` は(enum の `non_exhaustive` のため)外部 crate から値を構築・比較でき、`MachineConfig` は構造体の `non_exhaustive` により明示コンストラクタ(`unlimited()` / `with_max_steps(n)`)で構築し、`max_steps` フィールドは読み取れる、型を再利用して「同一エラー型」(要件 13.1)を満たせる

## Research Log

### 素朴実装(core)の契約の確認
- **Context**: オラクルとなる `brainfuck-core` の設計(`design.md` / `requirements.md`)から、最適化側が再現すべき契約を抽出する
- **Sources Consulted**: `.kiro/specs/brainfuck-core/design.md`、`requirements.md`、仕様書 §3 §5 §6 §10 §11 §12
- **Findings**:
  - `step()` の判定順序は「停止判定(`pc == len`)→ 上限判定(`steps >= limit`)→ 命令実行(検証→更新)」。エラーは状態不変
  - 上限エラーは `StepLimitExceeded { limit, pc }`、範囲外は `PointerOutOfBounds { pc, dp, direction }`。`pc` は命令添字(コメントを除いた有効命令の通し番号)
  - `run()` は上限到達を `Err` で返す(`StopReason::StepLimitReached` は返さない)。エラー後も同じ `step()` は同じエラーを返す
  - `,` の EOF は `0` を格納し、入力読取位置は進めない(`input_pos <= input.len()` が不変条件)
  - `Machine` は `Clone`/`PartialEq` を持つが、内部状態(`pc` 等)は `snapshot()` / 参照 API 経由でのみ観測できる
- **Implications**: 最適化側の「観測結果」は `Result<StopReason, RuntimeError>`、`snapshot()` の 5 項目、`tape()`、`output()`、`input_position()` の組。これを差分テストの同値比較単位とする

### 実行数の閉形式(素朴実装換算)
- **Context**: 融合・ループ最適化後も `steps_executed` を素朴実装と厳密に一致させ、上限境界を保存するため
- **Findings**(現在セル値 `v`、`m` = 走査ループの 1 反復あたりの移動命令数、`B` = 本体命令数):

  | 操作 | 素朴実装換算の実行数 |
  |------|----------------------|
  | `+`/`-` 連続(長さ k) | k(正味 0 でも k) |
  | `>`/`<` 同方向連続(長さ k) | k |
  | `.` `,` `[` `]`(単体) | 1 |
  | `[-]` | `v == 0` なら 1、そうでなければ `1 + 2v` |
  | `[+]` | `v == 0` なら 1、そうでなければ `1 + 2(256 - v)` |
  | 移動/加算/乗算ループ(開始セル正味 -1、本体 `B` 命令) | `v == 0` なら 1、そうでなければ `1 + v(B + 1)` |
  | 走査ループ(`m` 命令の同方向移動本体、最初に 0 となるまでの反復数 `k`) | `1 + k(m + 1)`(開始セルが 0 なら `k = 0`) |

  - 根拠: 素朴実装は `[` を 1 回実行し、各反復で本体 `B` 命令と `]` 1 命令を実行する。`]` が 0 で抜けるときに `[` へは戻らない(`jump[pc] + 1` へ飛ぶ)ので `[` は 1 回のみ
- **Implications**: 各操作は実行前に素朴換算コストを求められる。`コスト > 残り予算` なら素朴再生へ縮退する

### 融合の範囲とエラー位置
- **Context**: `><` のような逆向きの混在や、`>>>` の途中の範囲外で、`pc`/`dp` が素朴実装と変わらないか
- **Findings**:
  - 同方向の連続移動は、正味移動後の `dp` が範囲内なら途中も範囲内(単調)。範囲外なら素朴再生で途中までの移動と正しい `pc` を再現できる
  - 逆向きの混在 `><` を正味 0 へ畳み込むと、`dp = 29999` での `>` エラーが消える。よって逆向きの混在は融合しない
  - `+`/`-` の混在は、セル演算が失敗しない(ラップのみ)ため正味量へ畳み込んでもエラー位置・他セルに影響しない。ただし実行数は元の命令数で数える
- **Implications**: 移動の融合は同方向のみ。加減算は混在可

### 最適化ループの適用条件と範囲チェック
- **Findings**:
  - 移動/加算/乗算ループ: 本体が `+ - > <` のみ(入出力・括弧なし)、ポインタの正味移動 0、開始セルの正味変化が -1(mod 256)。反復回数は `v`(開始セルが 1 ずつ減って 0 になるため)、他セルへの加算は `v × factor`(ラップ)
  - 本体が直線(分岐なし)なので、`v != 0` の最初の反復で本体が到達する全相対位置(開始位置 0 を含む走査範囲 `reach_min..=reach_max`)が `dp` に対して範囲内かどうかで、範囲外エラーが発生するかが一意に決まる。`v == 0` では本体を実行しないので範囲チェックは不要(要件 8.6)
  - 開始セルの正味変化が -1 以外(`[--]`、`[-->>+<<]` など)は反復回数が `v × d⁻¹ mod 256` になる等、扱いが複雑で学習効果も薄いため最適化しない(一般ループのまま)
  - 走査ループ: 本体が同方向の移動のみ。0 を見つけるまでの反復数と各位置の範囲は線形走査で求まる。範囲外へ出る場合は素朴再生へ縮退
- **Implications**: 認識対象を `[-]` `[+]`、正味 -1 の移動/加算/乗算、同方向走査に限定する。`[+]` は正味 +1 の唯一の例として `Clear` で扱う

### 外部依存(ベンチ/乱数)の要否
- **Context**: 差分テスト用の擬似乱数、ベンチマーク計測のためのライブラリ(proptest / criterion など)を採用するか
- **Findings**: core は外部依存ゼロ・`unsafe` ゼロを設計方針とする。差分テストは(1)小規模網羅、(2)固定シードの擬似乱数、(3)パターン別テンプレートで十分に目的を達する。擬似乱数は xorshift で数行。計測は `std::time::Instant` と `std::hint::black_box` で足りる
- **Implications**: 外部 crate を追加しない(build-vs-adopt: 採用しない)。proptest の縮小(shrinking)機能は失うが、失敗時に生成ソースとシードを出力することで再現性を確保する

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| A. 事前計算 + 縮退経路(採用) | 操作ごとに素朴換算コストを事前計算し、予算/範囲が許さない場合のみ操作の先頭から素朴再生 | 観測的一致(エラー時の状態・`pc` 含む)を構造的に保証。ホットパスは単純 | 素朴セマンティクスの小さな再実装を 1 箇所持つ(差分テストで検証) | 縮退は必ず終端(エラー)の直前でのみ発生 |
| B. 失敗時に core の Machine で最初から再実行 | 範囲外/予算不足を検出したら、core の `Machine` を初期状態から実行して結果を返す | 実装が最小 | 最適化側の誤りを core が隠蔽し差分テストの意味が薄れる。実行時間が 2 倍。出力/テープの引き継ぎが不要でも「別実装」にならない | 却下 |
| C. 逆向き混在も含む正味移動の融合 + 最大/最小到達量で判定 | `><` などを畳み込み、到達範囲で範囲外判定 | 融合率が高い | エラー時の `pc`/`dp` を再現するにはさらに途中状態の復元が要る。学習価値に対し複雑 | 却下(同方向のみ融合) |
| D. 命令単位の最適化せず、ループだけ最適化 | 連続命令は素朴のまま | 実装が小さい | 要件 3 を満たさない | 却下 |

## Design Decisions

### Decision: 観測的一致の定義を「出力・テープ・種別」より強い「完全状態一致」とする
- **Context**: ブリーフは「出力、最終テープ、エラー種別」の一致を求め、エラー位置の扱いを設計で明確化するよう求めている。後続の `compiler-comparison` は終了状態を表示する
- **Alternatives Considered**:
  1. 出力・最終テープ・エラー種別のみ一致(エラー時の途中状態は不問)
  2. 上記に加え、エラー値のフィールド(`pc`/`dp`/方向/`limit`)、エラー時点のテープ・出力・`dp`・入力位置・実行数まで素朴実装と完全一致
- **Selected Approach**: 2。縮退経路(素朴再生)により、追加の複雑さを抑えて構造的に達成する
- **Rationale**: 比較画面で「エラー時も同じ状態」を示せる。差分テストが `==` 比較だけで済み、検証が単純。要件 5.2, 5.4, 7.4, 8.1, 8.3 を満たす
- **Trade-offs**: 縮退経路のための素朴意味論の再実装が必要(約 40 行)。差分テストで保護する
- **Follow-up**: 縮退経路は性能のためでなく意味保存のための安全弁であり、仮に過剰に起動しても結果は正しい(素朴意味論そのもの)。したがって FastPath の起動条件の誤りは性能劣化にとどまり、条件の不足(適用すべきでない操作を適用)だけが正しさを損なう。後者を上限掃引・左右端テストで重点的に検証する

### Decision: 実行数は「素朴実装換算」を正とし、「IR 操作実行回数」を別名で併記
- **Context**: 仕様書 §12 は、実行命令数の定義が異なる場合は比較画面に明示することを求める
- **Selected Approach**: `steps_executed`(素朴換算。素朴実装と常に同値)と `ir_ops_executed`(IR 操作の実行回数)を別フィールドで返す。`ir_ops_executed <= steps_executed`
- **Rationale**: 上限判定・差分比較・CLI/GUI の実行数との整合には換算値が必須。最適化の効果(反復の省略)は `ir_ops_executed` で示せる
- **Follow-up**: `compiler-comparison` は、AOT/WASM が換算値を計数できない場合に「換算なし」と表示するか、同じ換算で計数するかを自身の設計で決める。本 spec は 2 種類の名前と定義のみを提供する

### Decision: エラー位置 `pc` は常に素朴実装の命令添字
- **Context**: 融合・ループ最適化後の IR 添字と素朴の命令添字が異なる
- **Selected Approach**: すべての外部報告(`RuntimeError.pc`、スナップショット `pc`)は core の命令添字。各 IR 操作は `source_range()`(命令添字の半開区間)を持ち、変換は `src_start` で一意
- **Rationale**: エラーメッセージ・将来のデバッガ/比較画面が core の `source_offset` 変換をそのまま使える

### Decision: 外部 crate を追加しない / 縮退経路は同一 crate 内の公開モジュール `replay`
- **Selected Approach**: 依存は `brainfuck-core` のみ。縮退経路は `replay.rs` に隔離し、`state.rs`(`ExecState` が公開 `ReplayState` を保持)を介して `fast.rs` と状態を共有する
- **Rationale**: Simplification。trait による差し替え抽象は設けない(実装は 1 つ)

### Decision: 素朴再生とコスト式を公開し、下流の複製を排除する(クロス spec レビュー指摘への対応)
- **Context**: 素朴意味論の再生が core の `Machine::step`、本 crate の縮退経路、`compiler-comparison` の `brainfuck-wasm` の `replay.rs`(意図的な複製)の 3 箇所に存在し、コスト式・範囲条件も FastPath と WASM 生成部で二重に書かれる構成だった。複製間のずれは、差分テストで検出できても保守の負担と不一致リスクになる
- **Alternatives Considered**:
  1. 現状維持(下流が自前コピーを持つ)
  2. core に再生用の公開 API を足す(core の変更は禁止のため却下)
  3. 本 crate の再生を公開モジュール化し、下流が再利用する(採用)
- **Selected Approach**: 3。`replay` は `ReplayState`(検証付きの途中状態生成・読み戻し)、`Replayed`、`replay(program, limit: Option<u64>, start_pc, &mut state)` を公開する。コスト式は `Op::naive_cost(start_cell, scan_iterations)`、移動を伴う操作の範囲は `Op::static_reach()` に一元化し、FastPath も同じヘルパを使う
- **Rationale**: 再生は IR を知らない(`Program` と状態のみ)ので公開しても IR の内部事情を漏らさない。`ir_ops_executed` は `ReplayState` に含めず `ExecState` 側に置くことで、縮退経路が方式固有の実行単位数を更新できない構造を維持する。`Scan` の反復数 `k` は実行時のテープに依存するため、`naive_cost` は引数で受け取る
- **Trade-offs**: 公開面が増え、署名・意味論の変更が下流の再検証トリガになる(design.md Revalidation Triggers に明記)。WASM 側の生成コードは式を WASM 命令として書く必要があり完全な一元化はできないが、テストでは `naive_cost` をオラクルとして使える
- **Follow-up**: `compiler-comparison` は `brainfuck-wasm/src/replay.rs` を削除し、本 crate の `replay` へ置き換える

### Synthesis
- **Generalization**: 「連続命令統合」「クリア」「移動/加算/乗算」「走査」は、いずれも「前提条件を満たす区間を、素朴換算コスト付きの 1 操作へ置換する」という同一の枠組みとして実装でき、実行器はコスト付き操作を実行する一つの仕組みで統一する
- **Build vs Adopt**: 差分テスト用 PBT ライブラリ・ベンチ用フレームワークは採用しない(上記)。素朴インタプリタは新規実装せず core を再利用する(縮退経路の最小再実装を除く)
- **Simplification**: `step()` 相当の 1 操作ずつ実行 API は作らない(デバッガは素朴側の責務)。IR の最適化パスは「1 回の線形走査」にまとめ、パス間の中間表現は持たない。ピープホール(`Clear` + `Add` の `Set` 化等)は対象外

## Risks & Mitigations
- 公開 `replay`(素朴意味論の再実装)に不具合が入る — core を比較相手とする網羅/ランダム/境界テスト(特に上限 0..N+2 掃引、左右境界)で検出する
- 実行数コスト式の誤り(特に `[+]` の `256 - v`、走査の反復数)— 上限掃引テストで上限と実行数の境界を全数比較する
- 走査・乗算ループの範囲チェックの境界(off-by-one)— `dp` を 29999 付近へ運ぶ前置きプログラムを用いた境界テストを用意する
- 乱数テストが再現不能になる — 固定シード、失敗時にシードとソースを出力する
- ベンチが不安定で CI を壊す — ベンチは別ターゲット(`harness = false`)で、時間の大小を成否に使わない
