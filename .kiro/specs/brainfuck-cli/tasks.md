# Implementation Plan

> 前提: upstream の `brainfuck-core` spec の実装(ワークスペースのルート定義と、`Program` / `Instruction` / `Machine` / `MachineConfig` / `MachineSnapshot` / `StopReason` / `ParseError` / `RuntimeError` の公開 API)が完了していること。以降の `_Depends:_` に現れる番号なしの「core」はこの前提を指す。

- [x] 1. 基盤: CLI crate の雛形とサンプルプログラムを用意する
- [x] 1.1 CLI crate の雛形を作る
  - `crates/brainfuck-cli` を bin crate として定義する。依存は `brainfuck-core` への path 依存のみで、外部 crate は本番・dev とも追加せず、workspace の lint 設定を継承する(ワークスペースのルート定義は core 側が作成済みで、`crates/*` により自動的にメンバーになる。ルートは変更しない)
  - エントリには `unsafe` 禁止の宣言を置き、`error` / `args` / `source` / `input` / `app` の 5 モジュールを宣言し、各モジュールは空のファイルで用意する。`main` は後続タスクで接続するまで、何もせず終了コード 0 を返す仮の本体とする
  - ワークスペースのルートで `cargo build --workspace` と `cargo run -p brainfuck-cli` が警告・エラーなく成功する
  - `Cargo.toml` に外部依存が無く、`unsafe` を書くとビルドが失敗する構成になっている
  - _Depends: core_
  - _Boundary: Crate_
  - _Requirements: 11.3, 11.4_

- [x] 1.2 (P) `examples/hello.bf` を用意する
  - 設計書の Example に記載した検証済みの Hello World 文字列(`,` を含まない 1 行、末尾改行あり)を `examples/hello.bf` に置く
  - リポジトリルートの `examples/` ディレクトリを新規に作成する(steering の構造に従う)。core には依存しない(実行しての出力検証は 4.4 と 6.7 が担当する)
  - ファイルが 1 行で、命令文字(`><+-.[]`)のみからなり、`,` を含まず、`[` と `]` の個数が一致することを検索で確認できる
  - _Boundary: Example_
  - _Requirements: 10.1_

- [x] 2. 基礎型: 失敗の分類・終了コード・診断文を実装する
- [x] 2.1 `CliError` と終了コード、診断テンプレートを実装する
  - 終了コード定数(0 / 2 / 3 / 4)、引数エラー(欠落、余剰、未知、値なし、重複、矛盾、値の形式)、入出力の対象種別(プログラムファイル、入力ファイル、標準入力、標準出力)、CLI 全体のエラー(引数、括弧、実行、未完了停止、入出力)を定義する。入出力エラーは OS のエラーを保持する
  - 終了コードの対応を一箇所で決める: 引数・括弧 → 2、実行・未完了停止 → 3、入出力 → 4。0 と 2/3/4 以外の値を返さない
  - 診断文を設計書のテンプレート表どおりに実装する。core の括弧エラー・実行エラーは core の説明文をそのまま埋め込み、引数エラーは利用者の指定値を一切保持も表示もしない。入出力エラーは対象の役割名(`program file` など)と OS の説明のみを含み、パスは含めない。usage 案内で使うプログラム名は固定文字列 `brainfuck-cli` とする
  - モジュール内の単体テストで、全バリアントの終了コード、各診断文に原因語と数値(core 由来)が含まれること、引数エラーの診断に仮の指定値(例: 秘密めいた文字列)が現れないことを確認できる
  - _Depends: 1.1_
  - _Boundary: CliError_
  - _Requirements: 3.5, 3.6, 8.2, 8.3, 8.4, 8.6, 8.7, 9.1, 9.2, 9.3, 9.4, 9.5, 9.6, 9.7_

- [x] 3. 境界コンポーネント: 引数・ソース・入力を実装する
- [x] 3.1 (P) 引数解析を実装する
  - 引数の列(実行ファイル名を除く)から「使用方法の表示」または「実行オプション(プログラムパス、入力ファイル、解決済みの命令数上限、状態表示フラグ)」を決定的に構築する。命令数上限は `--max-steps N` なら N、`--no-step-limit` なら制限なし、どちらも無ければ既定 10,000,000 とする
  - 5 オプションを受け付け、`--name value` と `--name=value` の両形式、オプションとプログラムパスの順序入れ替え、値なしフラグの重複の冪等性を扱う。値付きオプションは次のトークンを内容によらず値として消費する。空の入力ファイル指定は値なしとして扱う
  - 引数エラーを検出する: プログラムパス欠落、2 個以上のパス、未知のオプション、値の欠落、値付きオプションの重複、`--max-steps` と `--no-step-limit` の併用、`--max-steps` の不正値(空、符号付き、非数字、`u64` 超過)。`--max-steps 0` は有効とする。エラー値は利用者の指定値を含まない
  - 最初の引数エラーを保持して走査を続け、`--help` があれば他の引数エラーより優先して使用方法の表示を返す。値として消費された `--help` は対象外。ファイルシステムには触れない
  - 使用方法の文字列(起動形式、全オプションの意味、`--max-steps` の既定値 10,000,000、終了コード 0 / 2 / 3 / 4 の意味)を定義する
  - モジュール内の表駆動単体テストで、全エラー経路、`--help` 優先、値として消費された `--help`、`=` 形式、順序入れ替え、`max_steps` の解決(既定 `Some(10_000_000)`、`--no-step-limit` が `None`、`--max-steps 0` が `Some(0)`)、非 UTF-8 のパス引数がパニックせず位置引数になることが確認できる
  - _Depends: 2.1_
  - _Boundary: ArgParser_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7, 1.8, 1.9, 1.10, 1.11, 2.3, 2.4, 6.1, 6.2, 6.5, 6.7, 6.8, 9.6_

- [x] 3.2 (P) ソース読み込みとバイト列解析を実装する
  - ソースファイルをバイト列として読み込む。失敗(不在、権限なし、ファイルではない)はプログラムファイルを対象とする入出力エラーにし、パスを保持しない
  - バイト列を加工せず core のバイト列解析(`Program::parse_bytes`)に渡す。0x80 以上のバイトは core がコメント扱いにし、位置は元のバイト位置のまま報告される。解析の括弧エラーは CLI のエラーへ包む。UTF-8 検証は行わず、BOM もコメントとして扱う。CLI 側に置換などの前処理は持たない
  - モジュール内の単体テストで、全 256 バイト値を含むソースが括弧エラー以外では失敗しないこと、0xFF や日本語(UTF-8)を含むソースの後ろの括弧エラーが元ファイルの実バイト位置のオフセットを示すこと、空ソース・コメントのみのソースが命令 0 個で成功すること、存在しないパスの読み込みが入出力エラー(対象はプログラムファイル、診断にパスを含まない)になることを確認できる
  - _Depends: 2.1_
  - _Boundary: SourceLoader_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6_

- [x] 3.3 入力の取得を実装する
  - 解析済みプログラムが入力命令を 1 個以上含むかを判定する関数を提供する
  - 3.2 とは独立している(3.1 の実行オプション型のみに依存する)
  - 入力を次の順で取得する: 入力ファイル指定あり → その全バイトを無変換で読む(失敗は入力ファイルを対象とする入出力エラー。標準入力には触れない)。指定なしかつ入力命令あり → 標準入力を EOF まで無変換で読む(失敗は標準入力を対象とする入出力エラー)。それ以外 → 空の入力で、標準入力には触れない
  - モジュール内の単体テストで、入力命令の有無の判定、読み出すと失敗する `Read` を使って「入力ファイル指定時」と「入力命令なし」では標準入力が呼ばれないこと、入力命令ありでは EOF まで読まれること、0x00 / 0xFF を含むバイト列が無変換で得られること、存在しない入力ファイルが入力命令の有無によらず入力ファイル対象の入出力エラーになることを確認できる
  - _Depends: 3.1_
  - _Boundary: InputLoader_
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.6, 4.7, 4.8_

- [x] 4. オーケストレーション: 実行・出力・診断・終了コードを実装する
- [x] 4.1 プログラムの実行と結果の整理を実装する
  - 解析済みプログラム・入力バイト列・解決済みの命令数上限から core の機械を生成する(上限ありは上限指定、なしは無制限の設定)。`run` を 1 回だけ呼び、成功・失敗にかかわらず、出力バイト列とスナップショット(`pc`・データポインタ・実行済み命令数)を取得して返す。実行意味論と上限判定は core に委ね、CLI で再実装しない
  - 停止理由の判定を実装する: 正常停止のみ成功とし、それ以外の停止理由(現状 core は返さない予約値)は未完了停止のエラー、core の実行エラーは実行エラーとして分類する
  - 状態表示の文字列(`state: pc=<N> dp=<N> steps=<N>` と改行)を、スナップショットの値をそのまま用いて整形する
  - モジュール内の単体テストで、`+++` を上限 3 で正常、上限 2 と 0 で上限超過、空プログラムを上限 0 で正常、`<` で範囲外の実行エラー(部分出力とスナップショットが取得できる)、予約された 3 種の停止理由が未完了停止(終了コード 3)に分類されること、状態表示の書式が確認できる
  - _Depends: 3.2, 3.3_
  - _Boundary: App_
  - _Requirements: 4.5, 6.3, 6.4, 6.6, 7.1, 7.2, 7.5, 7.7, 8.1, 8.6, 11.1_

- [x] 4.2 入口(引数処理)とパイプラインの前半を実装する
  - 標準入力・標準出力・標準エラーを注入できる形で、全体の入口(引数の列を受け取り終了コードを返す)を実装する。使用方法の指定なら使用方法を標準エラーへ書いて 0、引数エラーなら診断と使用方法の案内を標準エラーへ書いて 2。この段階では標準出力に一切書かない
  - 実行を固定順序(ソース読込 → 解析 → 入力取得 → 実行)で進め、最初に失敗した段の分類の終了コード(2 または 4)で終了する。実行に至らない失敗では標準出力と状態表示を出さず、診断を標準エラーへ書く(診断の書き込み失敗は無視し、パニックしない)。実行まで成功した場合は、4.1 の結果を受けて次のタスクの出力段へ渡す形にしておく
  - ファイルを必要としない単体テストのみを置く: 使用方法の表示が標準エラーのみで 0 になる、引数エラーが 2 で標準出力空、存在しないソースパスが 4 で診断にパスを含まない、`--help` がファイル読み込みを行わない。ファイルを要する段の優先順位の検証は 6.2 に任せる
  - _Depends: 4.1_
  - _Boundary: App_
  - _Requirements: 2.1, 2.2, 3.7, 8.8_

- [x] 4.3 出力・診断・状態表示・終了コード決定を実装する
  - 実行結果(出力バイト列、スナップショット、結果)と実行オプションを受け取り、標準ストリームへ書いて終了コードを返す出力段を、ファイルに依存しない独立した関数として実装し、4.2 の入口から呼ぶ
  - 出力が 1 バイト以上なら無加工で標準出力へ書き込みフラッシュする(0 バイトなら何も書かない)。実行エラーのときも部分出力を先に書き、その後に診断を標準エラーへ書く。`--dump-state` 指定時は状態表示を標準エラーへ書く(標準出力の書き込み結果によらない)。成功時かつ `--dump-state` なしでは標準エラーは空
  - 終了コードを決める: 標準出力の書き込み失敗 → 4(実行エラーがあれば両方の診断を書く)、実行エラー・未完了停止 → 3、正常停止 → 0。標準エラーへの書き込み失敗は無視する
  - 結果を直接組み立てて渡すモジュール内の単体テストで、書き込みに失敗する `Write` を使った 4(実行エラー併記、状態表示の出力を含む)、実行エラーでの部分出力と診断の順序、0 バイト出力で標準出力に書かないこと、成功時に標準エラーが空であること、`--dump-state` の有無による状態表示、同じ入力での再実行の一致(決定性)を確認できる
  - _Depends: 4.2_
  - _Boundary: App_
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 5.7, 7.3, 7.4, 7.6, 8.1, 8.5, 8.8_

  - 括弧不一致のソース、存在しないソースを渡すと、それぞれ終了コード 2 と 4 になる
