# Requirements Document

## Project Description (Input)
# Brief: desktop-gui-e2e-browser(要約。全文は同じディレクトリの `brief.md`)

## Problem
desktop-gui の自動テストは vitest + jsdom と Rust の統合テストだけで、実ブラウザで描画・操作するテストが無い。2026-11-07 の実機スモークでは jsdom では見つからない不具合(エディタのフォーカス枠が見えない、ガターの背景色、幅 1040 px での右カラムの切れ)が出た。実機スモークは一度きりの手作業で繰り返せない。レイアウト・CSS・フォーカス・描画・キーボード操作・ブラウザの既定動作の回帰を、毎回の変更で自動検出したい。

## Desired Outcome
`apps/desktop` で E2E 用のコマンドを実行すると、Chromium でアプリ画面を開き、実際の Rust バックエンド(`brainfuck-gui-api` の `DebuggerService` とファイル入出力)を通して操作し、手動スモーク(`apps/desktop/README.md` の 1〜15)のうち自動化できる項目が機械的に検証される。Linux の CI(GitHub Actions `ubuntu-latest`)で動き、WebView2 と Windows に依存しない。各スモーク項目の「自動化済み・手動のまま・対象外」が README と traceability で追跡できる。製品コードの変更は最小限で、spec に明記される。

## Approach
実 Rust を橋渡しする(A-1): `brainfuck-gui-api` を呼ぶテスト専用の stdio バイナリ(置き場は design で決める)、Node 側の中継、ブラウザ側の IPC 差し替え(`@tauri-apps/api/mocks`)。ネイティブダイアログはテストが指定した結果で代替する。

## Constraints
Node 26、Rust stable、`unsafe` 禁止。`npm test` に E2E を混ぜない。既定は headless。開発用ポート 1420 と衝突させない。時間計測の検証は余裕を持った閾値で別グループ(`@perf`)に分離する。開発 PC では新しい実行ファイルがウイルス対策ソフトに止められることがある。Markdown 成果物は日本語。

## Introduction

`desktop-gui-e2e-browser` は、完成済みの desktop-gui の画面を実際のブラウザエンジンで描画・操作し、実際の Rust バックエンドを通して振る舞いを確認する、繰り返し実行できる E2E テストスイートを提供する。対象の利用者は、desktop-gui とその後続(compiler-comparison など)を変更する開発者と、変更を取り込む前に回帰を確認する CI の運用者である。

本 feature は製品の機能を追加・変更しない。2026-11-07 に一度だけ手作業で行った手動スモーク(`apps/desktop/README.md` の「手動スモーク手順」1〜15)を、ブラウザで検証できる範囲で自動テストに置き換え、残りの項目について「手動のまま」「対象外」とその理由を記録する。実行の意味論(出力・`pc`・`dp`・実行数・エラー)は、テスト用に作り直したものではなく、アプリと同じ Rust の実装から得る。

以下、手動スモークの番号(例: 「スモーク 3.1」)は `apps/desktop/README.md` の「手動スモーク手順」の番号を指す。

## Boundary Context

- **In scope**:
  - E2E スイートの実行コマンド、実行環境の準備、失敗時の調査材料の保存、Linux の CI での実行
  - 実際の Rust バックエンドを通した画面操作の検証と、ネイティブダイアログ・ウィンドウを閉じる要求の代替
  - 手動スモーク 1、2、3.1、4〜13、14.1〜14.3、15 のうち、ブラウザで観測できる項目の自動化
  - 応答性(1 秒以内の更新・停止)の計測を、通常の検証とは別のグループとして実行すること
  - README の「検証結果の記録」への自動化状況の追記と、本 spec の traceability での手動スモーク番号との対応
- **Out of scope**:
  - 実アプリ・WebView2 でしか確かめられない挙動のうち、後続の `desktop-gui-e2e-webview` が扱うもの: 実ウィンドウの閉じるボタン(スモーク 11.1〜11.3、11.5)、実際のリロード(11.6)、WebView2 の右クリックメニュー(11.7)、Tauri の CSP の実効、実 WebView2 でのフォーカス枠の描画(13.3)、実 IPC での起動・実行・Pause の確認(1、3.1、4、9.3)
  - ネイティブダイアログの見た目とモーダル性(スモーク 10.1 のダイアログの部分)と、ウィンドウの最小サイズの強制(スモーク 12 の実ウィンドウでの縮小)。手動のまま(`desktop-gui-e2e-webview` も対象外)
  - スモーク 3.2(CLI との比較。Rust の一致テストが担う)と 14.4(スクリーンリーダーの読み上げ。手動のまま)
  - OS の設定そのもの(ライトテーマ・高コントラストモードの切り替え)の確認。ブラウザのメディア特性のエミュレーションで代替し、その旨を記録する
  - desktop-gui の機能追加・仕様変更・不具合修正、Rust の `DebuggerService` の API 変更
  - 基本 CI(Rust と フロントエンドの build / lint / test のワークフロー)の新設(`ci-baseline` の担当)
  - compiler-comparison の画面
- **Adjacent expectations**:
  - desktop-gui は、画面のアクセシブルな名前(ボタン名 `Run (F5)` など、領域名 `操作`・`状態`・`テープ`・`出力`・`入力`・`ソース`・`通知`、`role`)と、フロントエンドとバックエンドの間のコマンド名・引数・応答・エラーの契約を維持する。これらが変わった場合、本スイートは失敗として変更を知らせる
  - `brainfuck-gui-api` は、アプリが使うのと同じデバッガのサービスとソースファイルの検査・変換を提供し、本 feature はそれらを再実装しない
  - `examples/hello.bf` を実行した結果(出力 `Hello World!`、`pc` 106、`dp` 6、実行数 906)は、`brainfuck-cli` と desktop-gui の既存の検証で確定した期待値である
  - E2E が製品の不具合を見つけた場合、その修正は desktop-gui 側の変更として扱い、本 feature は失敗の記録と追跡のみを行う

## Requirements

### Requirement 1: E2E スイートの実行コマンドと実行環境
**Objective:** As a 開発者, I want 1 つのコマンドで E2E スイートを準備から実行まで行え、既存のテストとは分かれていること, so that 変更のたびに画面の回帰を手軽に確認でき、通常の単体テストの速さを損なわない

#### Acceptance Criteria
1. When 開発者が `apps/desktop` で E2E 用のコマンドを実行する, the E2E スイート shall 画面のビルド、テスト用バックエンドの準備、ブラウザでの全シナリオの実行を順に行い、結果を合否と件数で報告する
2. The E2E スイート shall 既存の単体テストのコマンド(`npm test`)の実行対象に含まれず、既存の単体テストのコマンドはブラウザやテスト用バックエンドの準備なしに従来どおり成功する
3. The E2E スイート shall 既定ではブラウザを画面に表示しないモード(headless)で実行し、開発者が明示的に指定したときだけブラウザを表示して実行する
4. The E2E スイート shall Windows と Linux のどちらでも、WebView2 や Tauri のウィンドウを起動せずに実行できる
5. The E2E スイート shall 開発用のサーバが使うポート(1420)を使わず、開発用のサーバが起動していても実行できる
6. When 複数のシナリオが並列に実行される, the E2E スイート shall シナリオどうしでバックエンドの状態(実行セッション、開いている文書、未保存の旗)を共有せず、各シナリオを初期状態から開始する
7. If 実行に必要な準備物(テスト用バックエンドの実行ファイル、ビルド済みの画面、ブラウザ)が見つからない, the E2E スイート shall 不足しているものと準備の方法を示すメッセージを出して失敗する
8. If シナリオが失敗する, the E2E スイート shall 失敗したシナリオの画面のスクリーンショットと操作の記録を、調査用の出力ディレクトリに保存する
9. The E2E スイート shall 型検査と lint の対象に E2E のコードを含め、テストの出力ディレクトリをバージョン管理・型検査・lint の対象から除外する

### Requirement 2: 実際のバックエンドを通した検証
**Objective:** As a 開発者, I want 画面の操作が実際の Rust の実装で処理されること, so that テスト用の作り物とアプリの振る舞いが食い違って「偽の合格」になることを防げる

#### Acceptance Criteria
1. When 画面がバックエンドのコマンドを呼ぶ, the E2E スイート shall アプリと同じ Rust のデバッガのサービスとソースファイルの処理で要求を処理し、アプリと同じ形の応答またはエラーを画面へ返す
2. While バックエンドが実行のバッチを処理している, when 画面が一時停止を要求する, the E2E スイート shall バッチの完了を待たずに一時停止の要求をバックエンドへ届け、アプリと同じく実行中のバッチを中断させる
3. When 画面がファイルを開く・保存先を選ぶダイアログを要求する, the E2E スイート shall ネイティブのダイアログを開かず、そのシナリオが事前に指定した結果(ファイルのパス、またはキャンセル)を使って処理を続ける
4. If シナリオが結果を指定していないのに画面がダイアログを要求する, the E2E スイート shall そのシナリオを失敗させ、予期しないダイアログの要求があったことを報告する
5. When シナリオがウィンドウを閉じる要求を模擬する, the E2E スイート shall アプリと同じ規則(バックエンドが記録した未保存の旗が立っているときだけ画面へ確認を求め、立っていなければ確認なしで閉じる扱いにする)で振る舞う
6. When 画面が終了の確定を要求する, the E2E スイート shall アプリを終了させる代わりに要求を記録し、シナリオがその回数を検査できるようにする
7. The E2E スイート shall 画面が呼んだバックエンドのコマンドの名前と順序を記録し、シナリオが検査できるようにする
8. If テスト用バックエンドが異常終了する, the E2E スイート shall 応答待ちの要求をすべて失敗させ、そのシナリオを失敗として報告する

### Requirement 3: 製品コードへの影響の最小化
**Objective:** As a 開発者, I want E2E のための製品コードの変更が無いか最小限で、どこを変えたかが明らかであること, so that 製品の振る舞いや配布物にテスト用の仕組みが混入しない

#### Acceptance Criteria
1. The E2E スイート shall 配布用のビルドと同じ手順で作った画面を検証の対象にする
2. The E2E スイート shall テスト用の差し替えの仕組みを配布用の画面のビルド成果物に含めない
3. The E2E スイート shall E2E のために変更した製品のソースと設定ファイルを、spec の設計に一覧として明記し、一覧に無い製品のソースを変更しない
4. The E2E スイート shall 配布されないテスト専用のバックエンドの実行ファイルを、アプリの配布物とインストーラに含めない
5. The E2E スイート shall 既存の型検査・lint・単体テスト・Rust のテストを、E2E の追加後も成功させ続ける

### Requirement 4: 起動と編集のシナリオ
**Objective:** As a 開発者, I want 起動直後の状態と編集の基本操作が実ブラウザで確認されること, so that 描画やフォーカスの回帰を見逃さない

#### Acceptance Criteria
1. When 画面が開かれる, the E2E スイート shall 文書のタイトルが `Brainfuck Studio` であること、Hello World のサンプルが編集領域に表示され文書の表示が「無題」であること、状態ラベルが「未開始」であること、Run・Step が有効で Pause・Reset が無効であることを検証する(スモーク 1)
2. When シナリオが編集領域に文字を入力・削除する, the E2E スイート shall 未保存の変更の表示が現れること、取り消しの操作(Ctrl+Z)で入力前の内容に戻ることを検証する(スモーク 2.1)
3. When カーソルが括弧に接する, the E2E スイート shall 対応する括弧の両方が強調され、対応の無い括弧は対応ありとは異なる表示になることを検証する(スモーク 2.2)
4. When 日本語や絵文字(サロゲートペア)を含む行の後ろの命令が現在命令になる, the E2E スイート shall 現在命令の強調がその命令の文字の上に表示されることを検証する(スモーク 2.3)
5. When 改行コードが CRLF のテキストを貼り付けた後に Step する, the E2E スイート shall 現在命令の強調位置が命令の文字からずれないことを検証する(スモーク 2.4)

### Requirement 5: 実行制御とエラー表示のシナリオ
**Objective:** As a 開発者, I want Run・Pause・Step・Reset と実行エラーの一連の流れが実際の実行結果で確認されること, so that 実行制御の回帰を毎回検出できる

#### Acceptance Criteria
1. When 初期の Hello World を Run する, the E2E スイート shall 出力に `Hello World!` が表示され、状態ラベルが「正常終了」、`pc` 106、`dp` 6、実行数 906 になることを検証する(スモーク 3.1)
2. When 命令数上限を「上限なし」にして `+[]` を Run する, the E2E スイート shall 上限なしの警告が表示されること、Pause で状態ラベルが「一時停止」になり実行数の増加が止まること、Run で再開して実行数が再び増えること、それぞれの時点でボタンの有効・無効が正しいことを検証する(スモーク 4)
3. When Step を繰り返す, the E2E スイート shall 1 回ごとに `pc` が進み状態が更新されること、ループの内外で命令の順序どおりに進むこと、終端で状態ラベルが「正常終了」になり Step が無効になることを検証する(スモーク 5.1〜5.3)
4. When 現在命令が編集領域の表示範囲の外へ進む, the E2E スイート shall 編集領域がスクロールして現在命令の強調が表示範囲に入ることを、Step とブレークポイント停止の両方で検証する(スモーク 5.4)
5. When 一時停止または停止の後に Reset する, the E2E スイート shall 状態ラベルが「未開始」に戻り出力と状態がクリアされること、ブレークポイントと入力が保持されること、実行中は Reset のボタンとショートカットが効かないことを検証する(スモーク 6)
6. When 命令数上限に達するプログラムを Run する, the E2E スイート shall 上限到達の実行エラーが状態・エラーの領域に表示されることを検証する(スモーク 8.4、15.1)
7. When 括弧の対応が取れていないソースを Run する, the E2E スイート shall 解析エラーの位置が編集領域で強調されることを検証する(スモーク 15.2)
8. When 実行エラーや解析エラーの後にソースを直して Reset・Run する, the E2E スイート shall 編集と再実行ができ、正常に終了することを検証する(スモーク 15.3)

### Requirement 6: ブレークポイント・入力・命令数上限のシナリオ
**Objective:** As a 開発者, I want ブレークポイントと入力設定の操作が実ブラウザのクリックとキー操作で確認されること, so that ガターやキーボードの扱いの回帰を検出できる

#### Acceptance Criteria
1. When シナリオがガターをクリックする、またはエディタで F9 を押す, the E2E スイート shall ブレークポイントのマーカーが付け外しされ、F9 ではカーソル以降で最初の命令に付くことを検証する(スモーク 7.1)
2. When ブレークポイントを置いて Run する, the E2E スイート shall その位置で停止して状態ラベルが「ブレークポイントで停止」になり、続けて Run すると同じ位置で止まらずに進むことを検証する(スモーク 7.2、7.3)
3. While フォーカスが入力欄にある, when F9 を押す, the E2E スイート shall ブレークポイントが切り替わらないことを検証する(スモーク 7.4)
4. When 入力の形式をテキストと 16 進で切り替える, the E2E スイート shall 表示と入力内容が対応し、プログラムが読む入力バイト列が切り替えの前後で変わらないことを検証する(スモーク 8.1)
5. If 入力に不正な 16 進(奇数桁、16 進でない文字)が入力される, the E2E スイート shall 理由が表示され、Run が無効になることを検証する(スモーク 8.2)
6. If 命令数上限に不正な値(0、負数、小数、空、数字以外)が入力される, the E2E スイート shall 理由が表示され、直前の有効な上限で実行されることを検証する(スモーク 8.3)

### Requirement 7: ファイル操作のシナリオ
**Objective:** As a 開発者, I want 保存・開く・名前を付けて保存の流れを、実際のファイルの読み書きで確認できること, so that ダイアログ以外のファイル処理の回帰を自動で検出できる

#### Acceptance Criteria
1. When シナリオが保存先を指定して保存(Ctrl+S)または名前を付けて保存(Ctrl+Shift+S)する, the E2E スイート shall 指定したファイルに編集内容が書き込まれ、未保存の表示が消え、文書の表示がファイル名(ディレクトリを含まない)になることを検証する(スモーク 10.1 のうちダイアログ以外、10.3)
2. When シナリオがダイアログのキャンセルを指定する, the E2E スイート shall ファイルが書き込まれず、未保存の状態が保たれることを検証する(スモーク 10.2)
3. If 保存先が書き込めない(読み取り専用のファイル、存在しないディレクトリ), the E2E スイート shall 原因つきのエラーが「操作エラー」の見出しの領域に表示され、編集内容が残ることを検証する(スモーク 10.4)
4. While 保存先の選択が完了していない, when シナリオが編集を続ける, the E2E スイート shall 保存の完了後も未保存の表示が残り、ファイルには保存を要求した時点の内容が書かれることを検証する(スモーク 10.5)
5. When 改行コードが CRLF のファイルを開いて保存する, the E2E スイート shall 保存後のファイルの改行コードが CRLF のまま保たれることを検証する(スモーク 10.6)
6. When UTF-8 として不正なバイト列(例: Shift_JIS)を含むファイルを開く, the E2E スイート shall 不正なバイトが置換文字で表示され、見出しが「通知」の通知が表示されることを検証する(スモーク 10.7)
7. If 1 MiB を超えるファイルを開く, the E2E スイート shall 読み込みが拒否されて上限超過のエラーが表示され、編集内容が変わらないことを検証する(スモーク 10.8)
8. While 未保存の変更がある, when 新規(Ctrl+N)または開く(Ctrl+O)を操作する, the E2E スイート shall 確認ダイアログが表示され、キャンセルで編集内容が残り、確定で操作が進むことを検証する(スモーク 10.9)

### Requirement 8: 閉じる確認とブラウザ既定動作の抑止のシナリオ
**Objective:** As a 開発者, I want 未保存の文書を失わせる操作が抑止されていることを毎回確認できること, so that 文書の喪失につながる回帰を防げる

#### Acceptance Criteria
1. While 未保存の変更がある, when シナリオがウィンドウを閉じる要求を模擬する, the E2E スイート shall 確認ダイアログが 1 回だけ表示されることを検証する(スモーク 11.1)
2. When 確認ダイアログで「キャンセル」を選ぶ, the E2E スイート shall 画面が開いたまま編集内容が残り、終了の確定が要求されないことを検証する(スモーク 11.2)
3. When 確認ダイアログで「破棄して閉じる」を選ぶ, the E2E スイート shall 終了の確定がちょうど 1 回要求されることを検証する(スモーク 11.3)
4. While 保存済みまたは無変更である, when シナリオがウィンドウを閉じる要求を模擬する, the E2E スイート shall 確認ダイアログを表示せずに閉じる扱いになることを検証する(スモーク 11.4)
5. When 確認ダイアログの表示中に閉じる要求が重ねて届く, the E2E スイート shall 確認ダイアログが二重に表示されないことを検証する(スモーク 11.5)
6. When F5 の押しっぱなし(自動リピート)、Ctrl+R、Ctrl+F5 が押される, the E2E スイート shall それらのキー操作のブラウザ既定動作が抑止され、ページが再読み込みされず、編集内容が残ることを検証する(スモーク 11.6)
7. When 編集可能でない要素の上で右クリックする, the E2E スイート shall ブラウザの既定のコンテキストメニューが抑止されることを検証し、編集可能な要素(エディタ・入力欄)の上では抑止されないことを検証する(スモーク 11.7)

### Requirement 9: レイアウト・キーボード操作・見た目のシナリオ
**Objective:** As a 開発者, I want レイアウト・フォーカス・配色の回帰を、実際の描画結果から検出できること, so that 2026-11-07 の実機スモークで見つかった種類の不具合を再発させない

#### Acceptance Criteria
1. When 表示領域が 800 × 600 と 1040 × 768 の場合, the E2E スイート shall 横方向にはみ出す内容が無いこと、各領域(操作・ソース・入力・テープ・出力・状態)の右端が表示領域の内側にあること、スクロールですべての操作に到達できることを検証する(スモーク 12.1)
2. When 表示領域が 800 × 600 の場合, the E2E スイート shall ツールバーのボタンが複数の行に折り返されることを検証する(スモーク 12.2)
3. When 表示領域が大きい場合(1920 × 1080), the E2E スイート shall 横方向のはみ出しが無く、各領域が重ならずに表示されることを検証する(スモーク 12.3)
4. When キーボードの Tab・Shift+Tab だけで移動する, the E2E スイート shall すべての操作領域とボタンに到達でき、移動の順序が画面の視覚的な順序と一致することを検証する(スモーク 13.1、13.2)
5. When キーボードの操作で各要素(エディタを含む)にフォーカスが移る, the E2E スイート shall フォーカスの枠が実際に描画され、他の要素に隠れていないことを、ライトとダークの両方の配色で検証する(スモーク 13.3)
6. When フォーカスのあるボタンで Enter または Space を押す, the E2E スイート shall Run・Pause・Step・Reset が動作することを検証する(スモーク 13.4)
7. When 配色をライトとダークに切り替える, the E2E スイート shall 主要な文字と背景のコントラスト比が 4.5:1 以上であることを検証する(スモーク 14.1 のブラウザでの代替)
8. When 強制配色(高コントラスト)を有効にする, the E2E スイート shall 枠・ボタン・フォーカスの枠・波線の下線が描画されていることを検証する(スモーク 14.2 のブラウザでの代替)
9. When 解析エラー・ブレークポイント・括弧の対応がある状態を表示する, the E2E スイート shall 波線の下線、枠、ブレークポイントのマーカー、括弧の一致表示が描画されていることを検証する(スモーク 14.3)

### Requirement 10: 応答性の検証と計測の分離
**Objective:** As a 開発者, I want 応答性の確認と時間の計測を分け、計測の揺らぎで通常の検証が不安定にならないこと, so that 通常の回帰検出を信頼でき、計測結果も別に確認できる

#### Acceptance Criteria
1. While 上限なしの無限ループを実行している, the E2E スイート shall 実行数の表示が増え続け、ボタンへのホバーとテキストの選択に画面が反応することを、時間の閾値に依存しない方法で検証する(スモーク 9.1)
2. The E2E スイート shall 時間の閾値を伴う検証(実行数の表示が 1 秒以内ごとに更新されること、Pause の後に出力とテープの表示が 1 秒以内に追いつくこと、Run の開始から Pause の受け付けまでが 1 秒以内であること)を、通常の検証とは別に実行できるグループに分ける(スモーク 4.2、9.2、9.3)
3. The E2E スイート shall 時間の閾値を伴う検証で、要件の 1 秒に対して余裕を持たせた閾値を使い、実測値を結果に記録する
4. When 開発者が通常の E2E 用のコマンドを実行する, the E2E スイート shall 時間の閾値を伴う検証のグループを実行しない

### Requirement 11: CI での継続的な実行
**Objective:** As a CI の運用者, I want E2E スイートが Linux の CI で自動的に実行されること, so that 画面の回帰を変更の取り込み前に検出できる

#### Acceptance Criteria
1. When main ブランチへの push またはプルリクエストが作られる, the E2E スイート shall Linux の CI ランナーで E2E スイートを実行し、通常の検証の失敗を CI の失敗として報告する
2. The E2E スイート shall CI で時間の閾値を伴う検証のグループも実行し、その失敗を結果に表示するが、CI 全体の失敗にはしない
3. If CI で E2E スイートが失敗する, the E2E スイート shall 失敗の調査用の出力(レポート、スクリーンショット、操作の記録)を CI の成果物として保存する
4. The E2E スイート shall CI の設定として自分の job だけを追加し、基本 CI(Rust とフロントエンドの build / lint / test)の設定を含めない

### Requirement 12: 追跡可能性と記録
**Objective:** As a 開発者, I want 手動スモークの各項目が自動化済みか、手動のままか、対象外かを一覧で確認できること, so that 実機での確認が必要な残りの項目を見落とさない

#### Acceptance Criteria
1. The E2E スイート shall 手動スモーク 1〜15 の各項目(枝番を含む)を、「自動化済み(検証するシナリオ)」「手動のまま(理由)」「対象外(担当する spec またはテスト)」のいずれかに分類した対応表を、本 spec の traceability に記載する
2. The E2E スイート shall ブラウザのエミュレーションで代替した項目(スモーク 14.1、14.2)について、OS の設定そのものの確認ではないことを traceability に明記する
3. The E2E スイート shall `apps/desktop/README.md` に、E2E スイートの準備と実行の手順、時間計測のグループの実行方法、開発 PC でウイルス対策ソフトが新しい実行ファイルを止める場合の対処(除外の設定または一時停止)を記載する
4. When E2E スイートを実行して結果を確認する, the E2E スイート shall その実施日と結果(件数、失敗、計測値)を `apps/desktop/README.md` の「検証結果の記録」に追記する
5. The E2E スイート shall desktop-gui の既存の traceability(`.kiro/specs/desktop-gui/traceability.md`)を変更しない
